### 1.2. Список сущностей и связи

1. **`Project` (Проект)** — проект, в рамках которого ведутся работы.
2. **`Employee` (Сотрудник)** — участники проектов, постановщики и исполнители задач.
3. **`Status` (Статус)** — справочник допустимых этапов задачи.
4. **`Task` (Задача / Подзадача)** — единица работы в рамках проекта.
5. **`Assignment` (Назначение на задачу)** — связь между исполнителем и задачей.
6. **`Comment` (Комментарий)** — обсуждение хода выполнения задачи.
7. **`TaskHistory` (История статусов)** — журнал аудита изменений статуса задачи.

**Типы связей:**

* `Project` → `Task`: **1:N**
* `Status` → `Task`: **1:N**
* `Task` → `Task` (подзадачи): **1:N**
* `Task` → `Assignment`: **1:N**
* `Employee` → `Assignment`: **1:N**
* `Task` → `Comment`: **1:N**
* `Employee` → `Comment`: **1:N**
* `Task` → `TaskHistory`: **1:N**
* `Status` → `TaskHistory`: **1:N**
* `Employee` → `TaskHistory`: **1:N**

## 2. Логическая модель данных

### 2.1. Идентифицирующие и неидентифицирующие связи

В проектируемой модели для всех таблиц используются суррогатные первичные ключи (`id SERIAL`).
**Все связи в модели являются неидентифицирующими**: внешний ключ (FK) родительской сущности является обычным атрибутом в дочерней таблице и **не входит** в состав её первичного ключа (PK). Концептуально сущности `Comment`, `Assignment`, `TaskHistory` являются зависимыми (слабыми), однако на уровне физической реализации они полностью автономны.

## 4. Частые запросы к базе данных (Бизнес-сценарии)

1. **Канбан-доска проекта:** Вывести список всех задач выбранного проекта, сгруппированных по статусу, с перечислением назначенных исполнителей и сортировкой по приоритету (`priority ASC`).
2. **Контроль дедлайнов:** Найти все задачи, у которых срок выполнения меньше сегодняшнего дня (`deadline < CURRENT_DATE`), а текущий статус не равен «Завершена». Вывести название задачи, проект и email исполнителей.
3. **Анализ рабочей загрузки (Workload):** Получить отчет по всем сотрудникам с подсчетом количества активных (не завершенных) задач, закрепленных за каждым из них.
4. **Аудит жизненного цикла задачи (Time-in-Status):** Для конкретной задачи вывести хронологию изменений статусов из `task_history` с указанием даты перевода, целевого статуса и сотрудника.
5. **Декомпозиция эпика:** Для выбранной родительской задачи (`parent_task_id IS NULL`) рекурсивно получить список всех её подзадач и подсчитать долю подзадач со статусом «Завершена».

# ЧАСТЬ 2: КОНТРОЛЬНАЯ РАБОТА №1

**Тема:** «Проектирование и базовый SQL. Агро-логистика: поставки кормов»

## 1. Концептуальная модель (Сущности и связи)

Выделено 5 сущностей. Для организации заказов кормов требуется промежуточная таблица, чтобы развязать связь "многие ко многим".

1. **Поставщики (suppliers)**
2. **Фермы (farms)**
3. **Корма (feeds)**
4. **Заказы (orders)**
5. **Позиции заказа (order_items)**

**Типы связей:**

* Поставщики → Корма: **1:N** (один поставщик предлагает разные корма)
* Фермы → Заказы: **1:N** (одна ферма делает много заказов)
* Заказы ↔ Корма: **M:N** (в одном заказе много видов корма, и один корм встречается в разных заказах). Эта связь разбивается на две связи 1:N через таблицу `order_items`.

---

## 2. Логическая модель и приведение к 3НФ

**Структура таблиц:**

* `suppliers`: id (PK), name, inn, region
* `farms`: id (PK), name, region, area
* `feeds`: id (PK), supplier_id (FK), name, type, calories
* `orders`: id (PK), farm_id (FK), order_date
* `order_items`: id (PK), order_id (FK), feed_id (FK), quantity

**Приведение к 3НФ:**
Модель изначально спроектирована в Третьей нормальной форме (3НФ).

* **1НФ:** Все поля атомарны, отсутствуют массивы или списки.
* **2НФ:** Используются суррогатные ключи (id). Неключевые поля зависят от первичного ключа целиком, частичных зависимостей нет.
* **3НФ:** Транзитивных зависимостей нет — все обычные колонки (например, регион или площадь) зависят напрямую от первичного ключа фермы или поставщика, а не друг от друга.

## 3. Физическая модель (DDL-скрипты)

```sql
CREATE TABLE suppliers (
    id SERIAL PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    inn VARCHAR(12) UNIQUE NOT NULL,
    region VARCHAR(100) NOT NULL
);

CREATE TABLE farms (
    id SERIAL PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    region VARCHAR(100) NOT NULL,
    area NUMERIC NOT NULL CHECK (area > 0)
);

CREATE TABLE feeds (
    id SERIAL PRIMARY KEY,
    supplier_id INT NOT NULL REFERENCES suppliers(id) ON DELETE CASCADE,
    name VARCHAR(150) NOT NULL,
    type VARCHAR(50),
    calories INT CHECK (calories > 0)
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    farm_id INT NOT NULL REFERENCES farms(id) ON DELETE CASCADE,
    order_date DATE NOT NULL
);

CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_id INT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    feed_id INT NOT NULL REFERENCES feeds(id) ON DELETE RESTRICT,
    quantity NUMERIC NOT NULL CHECK (quantity > 0),
    UNIQUE (order_id, feed_id)
);
```

## 4. SQL-запросы

**4.1 Вывести ID заказа, дату заказа и общее количество тонн кормов в каждом заказе:**

```sql
SELECT 
    o.id, 
    o.order_date, 
    SUM(oi.quantity) as total_tons
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
GROUP BY o.id, o.order_date;
```

**4.2 Вывести названия ферм, которые ни разу не делали заказы в 2023 году:**

```sql
SELECT f.name
FROM farms f
WHERE NOT EXISTS (
    SELECT 1 
    FROM orders o 
    WHERE o.farm_id = f.id 
    AND EXTRACT(year FROM o.order_date) = 2023
);
```
